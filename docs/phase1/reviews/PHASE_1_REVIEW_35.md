### Correction 1 — C-3 does not say whether the LWJGL confinement covers `mod.glue` subpackages, and five granted subpackages now host platform code

- **Sites:** `docs/phase1/v14/PHASE_1_DOC.md:2521-2523` (the softer-layer statement), `:2535-2536` (constraint C-3 as restated for every later phase), `:5674` (`SeamLwjglConfinementTest`'s asserted predicate in §8.1), `:5426` (§5.1's binding seam row).
- **Failure path.** C-3 reads 'no type under `org.lwjgl` outside **the package** `com.schmaloogium.mod.glue`'. §2.1 now grants five sibling homes under that name: `mod.glue.frame` — described at `:1766` as 'Minecraft/Forge frame adapters and **the LWJGL/platform bridge** for Phase 7'; `mod.glue.gl` (`:1770`) for Phase 14's sampler/DSA/debug/readback helper mechanisms; `mod.glue.vertex` (`:1768`) for the 'native vertex-input implementation'; plus `mod.glue.shadow` and `mod.glue.textures`. A bytecode scan implementing C-3 as written — exact package equality, which is the ordinary meaning of 'the package' in Java and the reading §4.5.2a itself uses when it insists that nested packages must be handled explicitly (V12-9, `:2767-2771`, `:6872`) — goes red on legal, granted tenants the moment P7's LWJGL bridge or P14's helpers land. Implemented as a prefix match instead, the constraint silently widens to every future `mod.glue.*` package without the document ever saying so. Either way the phase's own Impl-gate-adjacent seam test does not mean what its owner intends, and P7/P10/P13/P14 inherit an unresolvable instruction. This is not hypothetical drift: the document has already been bitten once by exactly this nested-package predicate ambiguity and recorded the lesson, but only for the Mixin config test.
- **Owner / receiver.** Owner: Phase 1 (§4.3, §8.1, §5.1). Receivers: Phase 7 (`mod.glue.frame`), Phase 8 (`mod.glue.shadow`), Phase 10 (`mod.glue.vertex`), Phase 13 (`mod.glue.textures`), Phase 14 (`mod.glue.gl`).
- **Minimal resolution.** State C-3 as a package **tree**: '`:mod`'s compiled classes reference no type under `org.lwjgl` outside `com.schmaloogium.mod.glue` **and its subpackages**', repeat the tree scope in the §4.3 softer-layer sentence and in §8.1's `SeamLwjglConfinementTest` row, and add the same words to §5.1's seam row so dependents inherit the enforceable form. No grant changes; no other constraint is touched.

### Correction 2 — D-P1-71 receives P14's materialization law without its label limb, while §4.7.4 still instructs callers to label at object-creation time

- **Sites:** `docs/phase1/v14/PHASE_1_DOC.md:3113-3126` (the D-P1-71 receipt), `:3811-3813` (the `DebugService` design bullet: 'Phase 4/5's object-creation sites can call `label(handle, "colortex0")` from day one'), `:5475` (§5.2's binding D-P1-71 row), `:4685-4693` (§4.7.8's debug-activity contract, which states the activity gate but nothing about object lifetime).
- **Failure path.** D-P1-71 makes `TextureService.create(debugLabel)` produce no native texture; only the first admitted `allocate` (or the known-2D first depth initialization) materializes and labels one. The document simultaneously keeps its standing instruction that creation sites call `DebugService.label(handle, …)` immediately. From v0.5, `DebugService.isActive()` becomes true on a capable backend with `schmaloogium.debug.glLabels` (§4.7.8), so that call is live GL. P1 nowhere states what `label` does when the handle is not yet materialized. A backend implementing P1's text alone must either issue `glObjectLabel` against a name that does not exist — a queued `GLError` landing in the very drain P5 and P13 are required to bracket their work with, which their contracts treat as failed evidence — or invent a retention rule P1 never granted. The resolving rule already exists on the receiving side and is exactly the limb this receipt dropped: `PHASE_14_DOC.md:1352-1361` ('`KhrDebugBackend.label(handle, name)` retains the label for an unmaterialized texture and issues `glObjectLabel` only for an existing native object … An explicit label update before materialization updates that retained value without GL'), reaffirmed at `:1665` and asserted by `DebugLabelCoverageTest` (`:2238`). P2 also expects to model 'logical create, target admission, materialization, label and storage' as distinct steps (`PHASE_2_DOC.md:2629`), which it cannot derive from P1's row.
- **Owner / receiver.** Owner: Phase 1 (§4.7.3 D-P1-71 text and §5.2's row own the caller-facing legality of every facade verb against a handle lifetime state). Receivers: Phase 14 (implements `DebugService`; already holds the correct law), Phase 5 and Phase 13 (labelling call sites at creation), Phase 2 (recorder/event modelling).
- **Exact missing semantics.** That `DebugService.label` on a live-but-unmaterialized owned texture handle is **legal**, updates the retained label, issues **no** GL and appends no native-label event; that the retained value — original or updated — is the one emitted once, after first exact-target materialization and before storage work; and that this changes nothing for foreign or borrowed handles, which are already materialized objects.
- **Minimal resolution.** One sentence appended to §4.7.3's D-P1-71 paragraph and the same clause added to §5.2's D-P1-71 row. No signature, verb, milestone or permission-matrix change; the wording can be taken from the received P14 law verbatim.

## 4. Notes (optional; no correction required)

- **N1 — the ordinary clear verb is not covered by D-P1-69's reasoning.** §4.7.4b normalizes rasterizer discard because 'a clean error drain alone cannot establish initialized contents' (`:4043-4047`). The same foreign-enabled discard silently defeats `StateService.clear(EnumSet<ClearTarget>)` (`:3411`), which P1 keeps and justifies by the reference pass structure (`:3654-3660`) and which carries no normalization and no stated limitation. No current phase document references `ClearTarget` outside P1, so there is no proven consumer today; if one appears, either the normalization or an explicit 'this verb does not normalize discard' sentence belongs beside it.
- **N2 — legacy attrib push/pop ordering relative to FBO rebinding is unstated.** §4.7.4b requires `glPushAttrib(GL_COLOR_BUFFER_BIT)`/`glPopAttrib` on the legacy path (`:4049-4056`) and separately requires restoring 'f's route before prior FBO bindings' (`:4058-4060`). Draw-buffer selection and colour write masks are per-framebuffer state; the document does not say the pop happens while `f` is still bound. Stating the bracket order would remove a real implementation-time ambiguity in an otherwise fully specified transaction.
- **N3 — the deletion law's binding scope could name framebuffer attachments explicitly.** §4.7.3's 'affected bindings/cache entries become zero' (`:3121-3123`) mirrors P14's wording (`PHASE_14_DOC.md:894-897`). GL detaches a deleted texture only from the currently bound framebuffer; attachments held by other, unbound estate FBOs are not detached. P5 owns the estate and would benefit from P1 saying which of the two it is promising.
- **N4 — §9 no longer enumerates the newest operations.** §9's service row (`:5832`) tags the interfaces `v0.1` and, as a matter of style, enumerates newly added operations inside the note; that enumeration stopped at the depth-attachment work. `clearColorAttachment`, `lockAlphaBlend`/`effectiveBlend`, `initializeSamplerUnits`/`prepareUnitBindings` and the `TextureParameters`/`TextureSpec` value families inherit their tag from the service rows, so no component is untagged — but a receiver reading §9 for milestone planning no longer sees them by name.
- **N5 — unexecuted-evidence limitation (mine and the document's).** This review is documentary. I executed no build, test, GL call or capture, and I verified no claim about native driver behaviour by running anything. The document is itself honest about this: §8's attempt-6/attempt-7 blocks are labelled 'planned, not executed', §12 claims no execution, and every recent §0 addendum states that changed §5 is unverified and that runtime proof remains a gate. Nothing in this report should be read as native, runtime or G6 parity evidence, and no hook result, optional async grant or final integration PASS is implied.
