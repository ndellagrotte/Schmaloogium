## 4. Findings

### C41-1 — Make ledger coverage match each named run’s capture domain

- **Severity:** correction.
- **Locations:** target §4.2.5, lines **706–709** and **728–736**; conflicting consumers are §4.8.3, lines **1521–1525**, and the `RUN-T2` row in §4.9, line **1545**. The compulsory PATH content is §3.4, lines **500–517**, and §4.3.3, lines **888–889**.
- **Claim:** the ledger’s unconditional per-scene sample rule cannot represent the intentionally static-only T2 gate.
- **Evidence and trigger:** §4.2.5 requires a PRIMARY record for every captured sample declared by every constituent scene, explicitly including motion-window coverage, and requires an authenticated comparison for every T2 PRIMARY. Each initial scene must contain a captured PATH. But §4.8.3 expressly excludes trustworthy manual PATH replay, and `RUN-T2` accepts only the milestone’s static SHOT set, with motion remaining a separate T1 run. Consequently even a fully successful, comparable static T2 execution lacks the required PATH T2 comparisons. Adding separate T1 motion evidence does not satisfy the specified T2 comparison requirement; omitting the PATH rows violates the index coverage rule.
- **Impact:** the prescribed T2 evaluator/run can succeed while its tier ledger necessarily remains incomplete/NOT_ATTEMPTED. The architecture gives the producer and final reporting consumer incompatible definitions of complete T2 evidence.
- **Required correction:** define and authenticate the expected capture/sample domain for each named run and tier. T2 must require exactly its declared static SHOT selection, while the independently mandatory motion gate retains complete PATH coverage. Apply the same domain to index completeness, comparison-kind validation, report labeling and the proposed ledger tests. Do not solve this by silently dropping motion coverage or manufacturing manual PATH oracles.
- **§5 impact:** **yes**. §5.1 exposes the tier definitions, named-run catalogue and evidence-index semantics to all behavioral phases. Their incorporated coverage contract must change coherently.

### C41-2 — Include world-generation settings in the generated-world cache key

- **Severity:** correction.
- **Locations:** target §4.5.1, lines **953–954**, and §4.5.5, lines **1263–1268**; accepted generation inputs are §4.3.2, lines **846–847**. The cache layout at line **1646** and environment receipt at lines **2213–2216** must remain consistent with the correction.
- **Claim:** the cache key conflates distinct legal scene world-generation requests.
- **Evidence and trigger:** scenes independently specify `worldType` and `generateStructures`, but both world-cache definitions select a save solely by `(seed, mcVersion, externalModSetSha256)` and generate only on a cache miss. Two valid scenes with the same tuple but different world types—for example default terrain and flat terrain—or different structure-generation settings therefore select the same already-generated save. The second request cannot obtain the world its generation fields describe. Hashing the copied save faithfully identifies the reused bytes; it does not distinguish the omitted generation requests or correct their selection.
- **Impact:** scene execution becomes dependent on which generation request populated the cache first. It can exercise the wrong terrain/structure environment while retaining an internally consistent copied-world hash. A changed scene hash forces reapproval, but does not force the requested world to be generated.
- **Required correction:** key generated saves by a canonical resolved world-generation descriptor that includes at least the admitted `worldType` and `generateStructures` values, alongside seed, Minecraft version and external-mod identity. Bind the retained save to that descriptor and update lookup/layout and proposed identity cases accordingly. Preserve the deliberate exclusion of subject-only engine rebuilds; do not replace the key with the full subject-bearing mod hash or indiscriminately key it by every capture-only scene field.
- **§5 impact:** **yes**. The exposed scene/capture contract and §5.1.1’s baseline/world-environment receipt incorporate this selection behavior. The descriptor/selection correction must be reflected in the binding receipt and any affected receiver expectations.
- **Historical distinction:** this omission is inherited from v1’s generation key, not newly caused by the correct full-versus-external mod identity split. It remains a current whole-document defect.

### C41-3 — Reconcile the cache layout with the canonical option-addressed image paths

- **Severity:** correction.
- **Locations:** target §4.10.3, lines **1649–1650**, against §4.7.2, lines **1383–1387**, §4.8.2, lines **1488–1489**, and the canonical image resolver in §4.2.6, lines **810–812**.
- **Claim:** the cache API’s published layout still specifies the obsolete single-image paths after the option-state/content-addressed cutover.
- **Evidence and trigger:** §4.7.2 requires baseline images beneath `sceneId/optionStateSha256/captureKind/captureId/sampleOrdinal/pixelSha256.png`, and §4.8.2 gives the corresponding option-addressed, content-addressed oracle path. §4.2.6 permits resolution only through those canonical paths. The cache layout nevertheless places baselines directly at `sceneId/captureKind/captureId/sampleOrdinal.png` and oracles at `sceneId/SHOT/shotId/sampleOrdinal.png`, omitting both option-state and raster-hash components. It is presented as the cache layout, without marking these entries obsolete or non-authoritative.
- **Impact:** following the cache-layout contract produces files the authenticated comparison resolver is required not to select. Its single raster leaf also cannot retain the distinct effective-option states and superseded raster evidence required by the repaired approval protocol.
- **Required correction:** update the cache-layout entries to the exact canonical §4.7.2/§4.8.2 paths, or remove the duplicate definitions and explicitly reference those authoritative grammars. Keep one placement contract across approval, cache operations, oracle capture and ledger reconstruction; no compatibility path or silent migration is needed.
